# Технические решения

## Исходная система

`ConfigService.save` проверяет документ общим валидатором SDK и ресурсами владельца, затем хранит нормализованный JSON. Таблица `GameConfig` уже содержит владельца, `title`, `gameId` и `document`. `LobbyService.create` валидирует исходный документ или собственный `configId` и записывает нормализованный снимок в `Lobby.config`. В DTO лобби игры могут скрывать содержимое правил. У Ёмифуды есть отдельное авторское чтение оригинала с `revealSecrets`. Сайт использует конструктор `NewLobbyPage`. Описания `info` и `tuning` уже хранятся в определениях всех пяти игр и доступны через `game_capabilities`. ## Решения

### T01. Хранение исходника и имени

- **Варианты.** Использовать существующую запись или завести отдельное хранилище черновиков.
- **Рекомендация.** Использовать `GameConfig`: сохранённый конфиг может менять статус в течение жизни.
- **Решение агента.** `GameConfig.document` хранит полученный JSON-объект без нормализации. `title` записи хранит имя библиотеки. `gameId` берётся из документа, а для отсутствующего или слишком длинного ID используется пустая строка. Таблицы и существующие данные сохраняют формат. Имя при новой записи можно вывести из `document.title` для старых клиентов, обновление без имени сохраняет текущую подпись. Лимиты документа и числа записей сохраняются. На маршрутах с конфигом транспорт допускает ещё 8 КиБ для полей запроса и его обёртки.

### T02. Проверка и статусы

- **Варианты.** Сохранять статус в БД или вычислять по текущим схемам и ресурсам.
- **Рекомендация.** Вычислять его при работе с библиотекой и при запуске.
- **Решение агента.** Использовать серверный валидатор для статусов `valid`, `invalid`, `unavailable`. Ошибки схемы и недоступные ресурсы дают `invalid`, временный сбой проверки даёт `unavailable`. Статус не хранится. Ошибки сохранения самого документа, например превышение лимита, отделены от статуса запуска. Выполнение по-прежнему получает только прошедший проверку и нормализованный снимок.

### T03. HTTP и MCP для личной библиотеки

- **Варианты.** Расширить существующие операции или завести параллельные команды для черновиков.
- **Рекомендация.** Расширить действующий контракт.
- **Решение агента.** HTTP `GET /api/configs` и MCP `config_list` возвращают метаданные со статусом, без JSON. Отдельный `GET /api/configs/:id` и `config_get` возвращают документ и диагностику. `POST` и `PUT` принимают документ и необязательное `name`, `PATCH /api/configs/:id` меняет имя. В MCP `config_save` принимает `config` для новой записи, `configId` для обновления, сочетание `configId` и `name` без документа для переименования. Новая запись по `lobbyId` требует имя. Доступ к записи и оригиналу проверяется на сервере.

### T04. Снимок из лобби и закрытые правила

- **Варианты.** Пересобрать конфиг из DTO или скопировать исходный серверный снимок.
- **Рекомендация.** Копировать из `Lobby.config` после проверки хозяина.
- **Решение агента.** HTTP `POST /api/lobbies/:id/config` и MCP `config_save` с `lobbyId` используют общий метод. Он читает снимок по ID без загрузки игрового движка, поэтому сохранит даже лобби со старой схемой. Для игр с закрытыми правилами обычное чтение и ответ записи используют безопасное представление. При несовместимой схеме правила скрываются целиком. Явное авторское чтение оригинала остаётся доступно хозяину записи. Статус вычисляется по оригиналу.

### T05. Создание и веб-редактор

- **Варианты.** Сохранить переключатели под расширенным режимом или заменить конструктор редактором JSON.
- **Рекомендация.** Использовать один редактор.
- **Решение агента.** `/new` принимает вставленный JSON, `?config=` открывает свою запись, справка может открыть рабочий пример в том же редакторе. JSON разбирается в браузере и проверяется сервером с задержкой. Ответ от предыдущего документа не влияет на текущий ввод. Создание и сохранение независимы. REST и MCP принимают ровно один из `config` и `configId`. Необязательное `name` для названия лобби остаётся для существующих клиентов, без него используется `title` документа.

### T06. Единый источник справки

- **Варианты.** Написать отдельные справки в компонентах сайта или использовать метаданные игр SDK.
- **Рекомендация.** Использовать метаданные SDK и примеры из версионированных пресетов.
- **Решение агента.** Игры добавляют примеры запросов рядом с `info` и `tuning`. Сайт использует `GET /api/games/:id/guide`, доступный аккаунтам и гостевым сессиям. Ответ содержит вводную, направления настройки, примеры запросов и рабочий JSON из демонстрационного пресета. MCP получает те же направления и примеры запросов через `game_capabilities`. Сайт ведёт в справку из списка игр и из лобби, в том числе из шторки партии. Правила сценария показываются существующей сводкой лобби.

## Зоны

Обновить карточки сайта, сервера, SDK, MCP и игр. Уточнить принцип единой схемы в видении. Проверить импорт и создание с сайта, сохранение из лобби и ремонт через MCP, доступ гостя к справке, скрытие закрытых правил, живую партию и изображение превью.

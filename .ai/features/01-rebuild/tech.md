# Технические решения

Автономный режим: решения принял агент, кроме помеченных «владелец». Версии библиотек
сверены с npm 2026-11-05. API библиотек сверяются по их типам в `node_modules` при реализации.

## Исходная система

Прототип `sandbox_games` (коммиты 2026-04-17…18, последний `aa2e83b`):

- `backend/` — Python, FastAPI, синхронный SQLAlchemy, Postgres с `JSONB`, Alembic, JWT.
  Зависимости нигде не закреплены: нет ни `pyproject.toml`, ни `requirements.txt`. Тестов нет.
- Игры: `backend/src/games/base_game.py` — `init_state(config, player_ids)` и
  `apply_move(state, user_id, move)`. Одна игра `tic_tac_toe.py`: `field_width`,
  `field_height`, `win_line`, два игрока. Схема настроек лежит в сиде БД
  (`games.config_schema`), а не рядом с кодом.
- Партии живут в словаре `active_games` в памяти процесса (`lobbies/service.py`)
  и теряются при перезапуске. Цикла тиков нет.
- WebSocket `/ws/lobby/{id}?token=…` — токен в строке запроса, рассылка снимков.
- `frontend/` — React 19 + Vite 7 SPA, `react-router-dom` 7, 750 строк CSS. Типы состояния
  крестиков-ноликов продублированы вручную в `pages/LobbyDetail.tsx`, там же отрисовка поля.

Сохранять почти нечего: задача переписывает всё с нуля (владелец разрешил не думать
об обратной совместимости).

## Решения

### T01. Язык

- Варианты: оставить Python на бэкенде; TypeScript везде.
- Рекомендация: TypeScript везде.
- **Решение (предложено в обсуждении, владелец не возражал):** TypeScript. Одна и та же
  логика игры нужна серверу (судья) и браузеру (подсветка ходов, а в играх реального
  времени — предсказание). Одна Zod-схема даёт проверку, типы, форму и JSON Schema для MCP.
  Игры на React можно будет встроить в Remotion для интеграции с Douga.

### T02. Структура репозитория

- Варианты: папки front/back; один пакет; монорепо на npm workspaces.
- **Решение:** монорепо npm workspaces:
  - `packages/sdk` — `@asobiba/sdk`: детали схемы, `defineGame`, движок партии, проверка,
    прогоны, описание возможностей. Без DOM и сети;
  - `games/tic-tac-toe` — `@asobiba/game-tic-tac-toe`: правила, схема, пресеты (`.`)
    и рендерер на React (`./client`);
  - `apps/server` — `@asobiba/server`: Fastify, Prisma, комнаты, WebSocket, MCP, превью;
  - `apps/web` — `@asobiba/web`: Vite + React SPA.

  Пакеты отдают исходники TypeScript (`exports` указывает на `src/*.ts`), шага сборки
  пакетов нет: сервер запускается через `tsx`, сайт собирает Vite, тесты — Vitest.

### T03. Сервер

- Варианты: Fastify; Hono; Express; Next.js с собственным сервером.
- **Решение:** Fastify 5 с `@fastify/websocket` 11, `@fastify/cookie` 11, `@fastify/static` 10.
  Один процесс отдаёт API, WebSocket, MCP и в продакшене собранный сайт.
  Next.js отброшен: поисковая оптимизация не нужна, а WebSocket в нём требует обёртки.

### T04. Сайт

- **Решение:** Vite 8 + React 19 + `react-router` 7, одностраничное приложение.
  В разработке Vite на :5173 проксирует `/api`, `/ws`, `/mcp`, `/files` на сервер :8787.
  В продакшене всё на :8787. Порт 3000 занят Douga и не используется.

### T05. База

- Варианты: Postgres; SQLite.
- **Решение:** SQLite + Prisma 6.19 (`prisma-client-js`). Нагрузки нет (владелец), Postgres
  не нужен, база — один файл `storage/asobiba.db`. Prisma 7 отброшена: требует драйвер-адаптеры
  и новый генератор, а 6.x знакома по Douga и поддерживает `Json` в SQLite с 6.2.
  Схема меняется миграциями (`prisma migrate`), а не `db push`: проект будет жить на сервере.
  Обёртка `scripts/prisma.mjs` подставляет абсолютный `DATABASE_URL` по умолчанию,
  чтобы не ловить относительные пути от папки схемы.

### T06. Схемы и проверка

- **Решение:** Zod 4. Каждая игра описывает `rules` и `visual` схемами Zod, SDK добавляет
  общие `series` и `timer`. Из одной схемы получаются тип TypeScript, разбор с подстановкой
  значений по умолчанию, ошибки с путём к полю и JSON Schema (`z.toJSONSchema`) для MCP
  и формы сайта. Вложенные объекты используют `.prefault({})`, чтобы их поля получали
  умолчания. Сообщения Zod — на русском через `z.config(z.locales.ru())`. Перекрёстные
  правила (длина линии не больше поля, клетки внутри поля) — функция игры `checkRules`.

### T07. Документ конфига

- **Решение:** версионированный JSON:
  `{ sdk: 1, game: "tic-tac-toe", gameVersion: 1, title, rules, series, timer, visual }`.
  `validateConfig` находит игру, сверяет версии, разбирает разделы, вызывает `checkRules`
  и возвращает нормализованный конфиг или список `issues` с `path`, `message`, `hint`.
  Ссылки на картинки (`{ asset: "ast_…" }`) собирает `collectAssetRefs`, а владение
  проверяет сервер. Неизвестная версия игры — ошибка с подсказкой взять схему заново.

### T08. Модель игры и движок

- **Решение:** игра — объект `defineGame` с чистыми функциями: `setup`, `applyAction`,
  `currentSeats`, `legalActions`, `roundResult`, `view`, необязательные `passTurn` и `tick`.
  Случайность — только из генератора с зерном (mulberry32), который движок передаёт в контексте.
  Движок `Match` поверх игры ведёт серию раундов, паузу между раундами (3 с), таймер хода
  с политиками `skip`/`random`/`lose` и фиксированный шаг для игр реального времени.
  Журнал хранит только действия людей с временем. Повтор = конфиг + зерно + время старта
  + журнал: `advance(t)` обрабатывает таймауты, паузы и тики по их собственному времени,
  поэтому восстановление после перезапуска даёт то же состояние.
  `nextWakeAt()` подсказывает серверу, когда разбудить партию.

### T09. Возможности для агента и прогоны

- **Решение:** `describeGame` отдаёт JSON Schema конфига, текст-руководство игры, слоты
  визуала, пресеты фигур и анимаций, готовые пресеты конфигов и лимиты. `simulate` играет
  N раундов случайными ходами с ограничением по числу ходов и сообщает: доля ничьих,
  победы по местам, средняя длина, проблемы `never-ends`, `always-draw`, `first-seat-dominates`.

### T10. Визуал и превью

- **Решение:** визуал — данные: тема, палитра, стиль поля, слоты (`{ preset, color }` или
  `{ asset }`), анимации `{ preset, durationMs, intensity }`. Рендерер крестиков-ноликов —
  React-компонент, рисующий SVG; анимации — CSS-классы с переменными. Превью на сервере:
  тот же компонент через `react-dom/server` → строка SVG (картинки встраиваются data URI)
  → PNG через `@resvg/resvg-js`. Позиция превью — начало или конец случайной партии с фиксированным зерном.

### T11. Картинки

- **Решение:** файлы в `storage/assets/<userId>/<assetId>.<ext>`, запись `Asset` в БД.
  Принимаем PNG, JPEG, WebP, GIF по сигнатуре; до 2 МБ и 2048 px по стороне (`image-size`).
  SVG от агента растеризуется в PNG через resvg; SVG со ссылками наружу
  (`href` не на `#` и не на `data:image/`) отклоняется. Импорт по ссылке — только http(s),
  без приватных адресов (проверка всех адресов DNS, редиректы вручную с повторной проверкой,
  тайм-аут, лимит размера), `ASSET_URL_ALLOW_PRIVATE=1` для тестов. Загрузка файла агентом —
  одноразовая ссылка `PUT /api/uploads/<ticket>` на 10 минут. Отдача — `GET /files/assets/<id>`
  любому вошедшему пользователю (id случайные).

### T12. Вход и права

- **Решение:** логин и пароль (`bcryptjs`), сессия — случайный токен в httpOnly-куке
  `asobiba_session` (SameSite=Lax), в БД хранится sha256. Регистрация только по одноразовому
  приглашению. Роли `admin` и `user`: админ создаёт приглашения. Личные токены MCP
  `asb_…` хранятся как sha256, их можно отозвать.

### T13. Комнаты и WebSocket

- **Решение:** `RoomManager` держит активные лобби в памяти: участников, партию, подписчиков
  и таймер пробуждения. Лобби, участники и партия с журналом лежат в БД; журнал пошаговой
  партии пишется после каждого принятого хода. При старте сервер восстанавливает пошаговые
  партии и прерывает партии реального времени. WebSocket `/ws` авторизуется сессионной
  кукой. Клиент шлёт `subscribe` и `action`, сервер — `lobby`, `match` (вид для конкретного
  места) и `error`. Вход, выход, старт и новая партия — через REST, после них рассылка.

### T14. MCP

- **Решение:** `@modelcontextprotocol/sdk` 1.32, `McpServer` и `StreamableHTTPServerTransport`
  без сессий (новый сервер на запрос, `enableJsonResponse`) на `POST /mcp` того же Fastify.
  Авторизация — `Authorization: Bearer asb_…`. Инструменты: `games_list`, `game_capabilities`,
  `config_validate`, `config_simulate`, `config_preview` (картинка PNG), `config_save`,
  `config_list`, `config_get`, `asset_list`, `asset_create_svg`, `asset_import_url`,
  `asset_upload_begin`, `lobby_create`, `lobby_list`, `lobby_get`, `lobby_close`.
  Инструкция в `initialize` не длиннее 3 КБ. Каждый вызов заново проверяет токен и владение.

### T15. Инструменты разработки

- **Решение:** TypeScript 5.9 (не 7.0: нативный порт вышел недавно, переход — отдельная мелочь),
  Vitest 5, tsx 4, concurrently для `npm run dev`. Тесты лежат рядом с кодом, интеграционные —
  в `apps/server/src/**/*.int.test.ts`. Тестовая база `storage/test/test.db` пересоздаётся
  миграциями перед прогоном, файлы идут последовательно. Тройка: `npm test` → `npm run build`
  → `npx tsc --noEmit` (один корневой `tsconfig.json` на все пакеты).

### T16. Старый код

- **Решение:** `backend/` и `frontend/` удаляются целиком. Данные Postgres не переносятся.

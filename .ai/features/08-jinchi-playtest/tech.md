# Технические решения

Статус: приняты агентом в разрешённом автономном режиме 16 ноября 2026.
Основание — [принятый продукт](product.md), P01–P18 и A01–A30.

## Исходная система

Проверены карточки dev-env, sdk, games, server, mcp, web и соответствующий код.
Работа идёт в основном чекауте, ветка `feat/08-jinchi-playtest`; рабочие порты
8787/5173 свободны на момент начала. GitHub origin доступен через gh.

- `rules.ts` Jinchi: строгая схема v1, map.rows, MAX_SIDE=200, dice.sides=2…20.
  `game.ts` хранит обычные числовые cells/bases, прямоугольники ищутся через SAT,
  автопропуски после 256 бросков используют точную вероятностную модель.
- `Match.outcome` вызывает `legalActions` только для проверки существования хода;
  timer random, simulate и preview также перечисляют все позиции. Это лишние
  массивы на большой карте. `diceModel` перебирает размеры с обходом всей карты.
- Локальный read-only замер текущего движка: setup 1000² — 75,7 мс, поиск —
  29,2 мс, JSON view — 7 003 565 байт. Сеть передаёт и immutable rules, и оба
  миллионных массива. Последний большой захват добавляет массив индексов.
- SVG использует серии одинаковых клеток, но UI строит его дважды — поле и
  миникарта. Предварительный resvg-замер миллионной карты: markup 31 мс,
  растеризация 155 мс. Статическое SVG сохраняем; интерактивный слой меняем.
- `presentRules` Pole и Quizor скрывает ответы. Quizor возвращает намеренно
  урезанную сводку, непригодную для полной валидации или построения новой сводки.
- `LobbyService` имеет оригинальный config и персональный `Match.view`;
  `routes.ts` сериализует сообщения, `useLobbySocket` принимает их. Seed партии
  в `MatchView` не передаётся, поэтому существующий серверный RNG пригоден для
  неизвестных исходов. Public seed генерации отделён от seed партии.
- Новые внешние зависимости не нужны. Проверены первичные документы
  [drawImage](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/drawImage),
  [putImageData](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/putImageData),
  [ResizeObserver](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver).

## Решения

### T01. Версии и совместимость

- Варианты: аддитивное расширение v1 / новая версия с миграцией всех конфигов.
- Рекомендация и **решение агента:** сохранить `gameVersion: 1`, поскольку поля
  необязательны и старые значения сохраняют семантику. Новый конфиг использует
  новые пресеты явно. Старые правила остаются без флагов/эффектов; info не добавляется
  default-объектом. Расширение остаётся внутри существующей версионированной схемы.
- `dice.sides: number | [number,number]`, каждое число 2…100, default 6.
  `diceSides(rules): [number,number]` нормализует только доступ к значениям.
  Старое число не превращается в массив при сохранении. Для legacy сохраняются
  порядок RNG и порядок пар точного ускорителя, чтобы журналы воспроизводились.

### T02. Флаги и эффекты как данные

- Варианты: отдельные режимы-игры / независимые секции правил текущей игры.
- **Решение агента:** `flags: {mode:'off'|'primary'|'bonus', value, target, positions}`;
  `effects: {cells, mysteryPool}` с безопасными default off/empty.
- `CellPosition={x,y}`, `EffectKind='cache'|'trap'|'reroll'|'lock'`,
  `EffectCell={x,y,kind:EffectKind|'mystery',value?}`,
  `WeightedEffect={kind:EffectKind,value?,weight}`. Пределы — из продукта.
- State сохраняет `scores` как клетки; добавляет `points`, `flagCounts`,
  `effectPoints`, `rerollCharges` (массивы по местам), оставшиеся `flags`/`effects`,
  `rerolled`, pending `rotationLocked[]` и текущий `turnRotationLocked`.
  View дополнительно даёт `canReroll`, `canSkip`, `canRotate`, `impossibleRoll`.
- Действия `reroll` и `skip-impossible`. Проверка сервера авторитетна. Очки,
  выбывание и приоритет победы точно соответствуют P12. Незнакомые исходы выбираются
  только при активации RNG партии; будущих исходов нет в публичном state.

### T03. Геометрия и вычисления

- Варианты: увеличивать пределы без изменений / линейные алгоритмы и ограниченные запросы.
- **Решение агента:** выделить `placement.ts` и `capture.ts`, без UI-зависимостей.
- `captureTerritory({width,height,cells,bases,rules},seat)` — единая реализация
  окружения для партии и проверки генератора. Итеративная заливка labels/sizes,
  один typed queue, без массивов массивов клеток и spread миллиона аргументов.
- `placementCapacity(state,seat): number[]` — профиль максимальной ширины по высоте,
  строящийся линейно по histogram разрешённых клеток и SAT приграничных клеток.
  Он проверяет все пары d100 без 10 000 обходов карты.
- `findPlacements(state,seat,rotated?,limit=Infinity)` поддерживает ограниченный
  вывод подсказок. `hasLegalAction(state,seat,ctx)` и `sampleAction(state,seat,ctx)`
  — необязательные hooks GameDefinition. Match/таймер/simulate/preview используют
  их, сохраняя fallback для прочих игр. Семантика legalActions остаётся прежней.

### T04. Генератор и баланс

- Варианты: генерация строк силами агента / общий детерминированный генератор.
- **Решение агента:** `generationSchema` и `generateMap(request)` в `generator.ts`;
  вход: width,height,shape,players,seed,diceSides,wallDensity,structures,balanced,
  flags/effects. Результат содержит map, flags, effects и явную диагностику.
- `analyzeMap(rules)` в `balance.ts` не импортирует game; использует placement/capture.
  Возвращает метрики по базам, issues и balanced. Проверяет площадь, стартовые
  броски, независимые выходы, связность, локальную площадь, пути, цели и первые
  захваты. Геометрические проверки предшествуют балансировке.
- Базы — по секторам вокруг общего центра. Структуры повторяются в полярных
  секторах с детерминированными вариациями и растеризацией; защита стартов и
  альтернативных коридоров предшествует заполнению препятствий. Проверки определяют
  результат, а не обещание визуальной симметрии. Ограниченное число попыток;
  невозможно — явная ошибка с исправлениями, параметры не меняются молча.
- Метаданные карты: `expectedPlayers?`, `generation?: {version:1,seed,balanced,
  players,shape,wallDensity}`. При заявленном балансе `checkRules` проверяет метрики
  заново и seats имеет min=max=expectedPlayers. Ручная правка снимает сертификат
  и показывает пересчитанную диагностику. Генератор возвращает данные, не код.
- MCP `jinchi_generate` получает компактный запрос и возвращает configId,
  метрики/summary и параметры; не печатает миллион строк. Следующие инструменты
  config_validate/simulate/preview получают config или configId. Генерация не
  создаёт лобби без отдельного вызова. HTTP `POST /api/games/jinchi/generate`
  обслуживает сайт тем же кодом; оба пути проверяют аккаунт и владение.

### T05. Сеть

- Варианты: полный JSON всех массивов на каждый ход / обратимая упаковка на границе.
- **Решение агента:** `wire.ts` в пакете Jinchi кодирует cells/bases как серии
  одинаковых значений с fallback на строку одного символа на клетку; lastMove —
  диапазоны индексов. Внутри движка и React остаются обычные массивы.
- Упаковка только в WS send, распаковка в useLobbySocket до передачи доске.
  Каждое сообщение — самостоятельный снимок: reconnect не зависит от пропущенной
  дельты. Immutable rules сохраняются в snapshot при необходимости; по замерам
  допускается удалять дубли map.rows с восстановлением из preceding lobby DTO.
  Кэш упаковки по immutable ссылке массива не делится между разными состояниями.
- На HTTP/WS вне Jinchi протокол не меняется. Проверяются длины/пределы decode;
  упаковка не затрагивает права или персональные поля view.

### T06. Общая информация

- Варианты: собирать текст на клиенте из публичных rules / белый список сервера.
- **Решение агента:** SDK `info.ts`: `GameInformation`, `TuningDirection`,
  `ConfigSummary`, `ConfigInformation`, `describeConfig(game,config)`.
  GameDefinition получает info/tuning/summarizeConfig. У каждой игры свой info.ts.
- capabilities отдаёт постоянную карточку и 5–7 направлений с последствиями;
  успешная validate отдаёт summary; LobbyDto.information строится из original config.
  Авторское `config.info?:{title?,text?}` — обычный текст до 80/2000 символов.
- Quizor/Pole summarizers используют только разрешённые поля; никаких raw walks,
  копирования вопросов, ответов, медиассылок и названий будущих сюрпризов.
- Общий React GameInformation используется в ожидании и сценической панели;
  `MatchStage.information?:ReactNode`. Quizor получает поля автора вне SchemaForm,
  поскольку его форма сейчас отдельная. Публичное приглашение не раскрывает автора.

### T07. Доска и редактор

- Варианты: полный SVG на каждом кадре / Canvas для игры, SVG для PNG.
- **Решение агента:** cached one-pixel-per-cell texture, Canvas drawImage для поля
  и миникарты, SVG overlay для ghost/объектов. Серверный SVG остаётся для resvg.
  Новых зависимостей нет. Hint/lastMove rendering ограничен, объекты агрегируются.
- `GameClient.stageHud?:'board'` позволяет Jinchi убрать дубли общей сцены.
  Счёт compact/details/hidden, миникарта и звук хранятся на устройстве. Turn cue
  ключ round/turn/seat, без dice; таймер отдельно от карты. Компоновки P01–P03.
- Камера сохраняет логический центр и клеточный масштаб при resize/fullscreen;
  никаких fit при чужих ходах. Тач <12px приближает, не ставит. 44px кнопки.
- MapEditor получает необязательные rules/onRulesChange и generator slot;
  поддерживает слой объектов и undo/redo. Изменяются затронутые строки,
  flood — typed queue, диагностика на границе жеста. Resize показывает потери.

### T08. Проверка и вливание

- **Решение агента:** TDD для новых правил, интеграционные тесты MCP/HTTP/WS,
  отдельные измерения максимальной карты. Полная тройка строго по verify.
  Живая приёмка через действующий сервер, браузер, настоящий MCP и несколько WS.
- Устройства фиксации: этот Mac и доступная браузерная мобильная эмуляция;
  эмуляцию честно отличаем от физического телефона. Разрешения A01–A03,
  fullscreen и отказ, реальные жесты, PNG, итог партии и reconnect.
- Существенный дефект/красный QG запрещает merge. После исправлений свежая тройка.
  В автономном режиме зелёный результат и свежее ревью разрешают PR и merge.

## Зоны изменения

SDK, игры (основной объём Jinchi; info для остальных трёх), MCP, сервер/протокол,
сайт. Карточки этих зон обновляются последней задачей плана. Схема БД, assets
и douga-контракты не меняются.

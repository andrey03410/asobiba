# Технические решения

Решения приняты агентом 2026-11-12 в разрешённом автономном режиме.
Основание — принятый [продукт](product.md).

## Исходная система

Прочитаны `auth/service.ts`, `routes.ts`, `app.ts`, `lobbies/service.ts`, Prisma-схема,
контракт API, контекст входа, маршруты сайта, страница лобби и её WebSocket-хук.
Карточки зон: server, web, assets, mcp, dev-env.

- `User.login` уникален, пароль обязателен; `role` сейчас admin/user. Членство и
  `Match.seatUsers` ссылаются на идентификатор пользователя, поэтому отдельная таблица
  игроков потребовала бы переделки комнат. Сессия — хеш случайной куки на 30 дней.
- HTTP использует общий `requireUser`, WebSocket запоминает `req.user` при открытии.
  Удаление сессии сейчас не отзывает открытый сокет.
- Изменения лобби сериализуются его замком. Комната хранит игроков текущей партии;
  имена берутся из текущего членства, отдельного снимка имён пока нет.
- Картинки доступны любому вошедшему по случайному ID. SDK `collectAssetRefs`
  собирает ссылки на картинки из документа конфига.
- Сайт монтирует лобби только после общего `RequireAuth`; выход сбрасывает UI даже
  при серверной ошибке. Между вкладками нет синхронизации личности.
- Существующие интеграционные тесты поднимают настоящий Fastify и WebSocket с
  отдельной SQLite-базой. React-компоненты проверяются серверным рендером.

## Решения

### T01. Представление гостя

- Вопрос: расширить User или ввести второй тип участников во всех комнатах?
- Варианты: **А. User с ролью guest, nullable passwordHash и displayName.** Б. Отдельный Guest.
- Рекомендация и **решение агента:** А. Внутренний login гостя имеет недоступный обычным
  логинам префикс `@guest:`; наружу `UserDto.login` возвращает отображаемое имя.
  `Role` аккаунтов остаётся admin/user; `UserDto.role` дополнительно принимает guest.
  Проверка пароля и выдача/проверка MCP-токенов исключают гостей.

### T02. Приглашение и первый вход

- Вопрос: открывать полный конфиг до представления?
- Варианты: **А. Публичный GET `/api/lobbies/:id/invitation` с кратким DTO.** Б. Публичное полное лобби.
- Рекомендация и **решение агента:** А. Только ID, название, игра, хозяин, статус,
  число мест и игроков; никаких участников, конфига и партии.
  POST `/api/auth/guest` принимает `{ name, lobbyId, role, attempt }`, создаёт сессию
  и вступает выбранной ролью. Действующая сессия используется без подмены.
  При гонке со стартом/заполнением ответ сохраняет куки уже созданного гостя,
  но сообщает ошибку вступления. Клиент обновляет `/api/me`, сохраняя имя и ошибку.

### T03. Повторы и ограничения первого входа

- Вопрос: как не создавать несколько гостей при повторе запроса?
- Варианты: **А. Случайный attempt и ограниченный кеш результата создания в одном процессе.** Б. Новая личность при каждом запросе.
- Рекомендация и **решение агента:** А. Клиент разделяет криптографически случайный pending attempt
  между первыми формами вкладок; сервер переиспользует одну операцию создания и куки до 10 минут.
  Ключ — секрет повтора, не печатается в логи. Повтор отозванной сессии не оживляет её.
  Новые входы ограничены 30 попытками с адреса за 15 минут; повтор текущей личности
  не создаёт новую. Имя проверяется по P04, Unicode учитывается по кодовым точкам.

### T04. Права гостя и картинки

- Вопрос: достаточно ли скрыть кнопки аккаунта?
- Варианты: **А. Отдельные проверки аккаунта на сервере и в маршрутах сайта.** Б. Только UI.
- Рекомендация и **решение агента:** А. Общий requireUser допускает гостя для лобби,
  requireAccount защищает списки, создание, конфиги, картинки и токены.
  Просмотр конкретной случайной ссылки разрешён гостю; `LobbyVisit` сохраняет открытые
  им лобби без занятия места. Картинка доступна гостю, только если входит в показанный
  конфиг посещённого лобби. Кабинет и каталог остаются доступны только аккаунтам.

### T05. Смена личности и живые соединения

- Вопрос: как исключить ходы старой сессии после выхода?
- Варианты: **А. Сериализация операций сессии и активный отзыв сокетов.** Б. Ждать переподключения.
- Рекомендация и **решение агента:** А. Операции входа в лобби, подписки, ходы и выход
  проходят под замком сессии и повторно проверяют её. Выход удаляет сессию и немедленно
  закрывает её сокеты с 4401; отдельный таймер закрывает их при истечении срока.
  Гостевые членства очищаются под замком каждого лобби, кроме игроков идущей партии.
  При активных партиях сервер требует `confirmActive: true`, иначе 409 с объяснением.
  Вход/регистрация при действующей личности требуют предварительного выхода.

### T06. Имена и история партии

- Вопрос: откуда брать имя после освобождения места гостем?
- Варианты: **А. Устойчивый номер гостя в членстве и снимок имён при старте.** Б. Только текущее членство.
- Рекомендация и **решение агента:** А. `LobbyMember.guestNumber` назначается под замком;
  гости отображаются как `Имя · гость N`. `Match.seatNames` сохраняет подписи мест
  при старте, DTO отдаёт их и после завершения. Данные гостя не удаляются каскадно
  при выходе: идентификаторы и история не должны пропасть.

### T07. Сайт и синхронизация

- Вопрос: как переключать приглашение и обычное лобби?
- Варианты: **А. Маршрут входа в лобби выбирает публичное приглашение или существующий LobbyPage.** Б. Копия всей страницы.
- Рекомендация и **решение агента:** А. Новая форма приглашения получает краткий DTO,
  предлагает имя и вход/наблюдение. Текущий LobbyPage переиспользуется для обеих личностей.
  Ключ компонента — ID личности, чтобы старая доска сбрасывалась при смене.
  Изменение входа передаётся вкладкам событием localStorage без данных пользователя;
  вкладки заново читают `/api/me`. Повторная проверка при фокусе и 4401.
  Ошибка выхода сохраняет текущую личность. Общие действия сессии доступны в шторке
  сцены; путь возврата — только внутренний через существующий safeNext.

## Миграция и зависимости

Используются текущие Prisma/Fastify/React, новые библиотеки не нужны. Аддитивная миграция
сохраняет аккаунты, лобби и партии; nullable пароль допускается только для гостя на уровне
сервиса. Новые поля у старых партий получают пустой снимок с fallback на текущих участников.
Локальные API библиотек используются по уже работающим образцам проекта.

## Уточнение после ревью I1

Две независимые формы могли послать разные attempt до первого Set-Cookie. Исправление:
смена входа сериализуется [Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API),
а гостевой запрос заново читает `/api/me` после получения замка. Pending attempt общий
в localStorage под этим замком; без Web Locks ключ атомарно создаётся в `readwrite`
[транзакции IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IDBDatabase/transaction).
Завершённый вход и успешный logout удаляют ключ; потерянный ответ без куки сохраняет
его для повтора из другой вкладки. Поэтому удаление куки после завершённого входа
не восстанавливает старую личность. Runtime-зависимости не добавлялись.

## Important

### I1. Две вкладки первого входа создают разные личности и могут отнять уже занятое место

**Место:** `apps/web/src/pages/LobbyEntryPage.tsx:17`,
`apps/server/src/routes.ts:99–108`.

`attempt` создаётся отдельно в каждом экземпляре формы. Сервер проверяет текущую
личность по куки входящего запроса; два запроса, отправленные до получения первого
`Set-Cookie`, оба проходят ветку создания гостя. Кеш в `AuthService.createGuest`
объединяет только одинаковые attempt, а здесь они разные. Замок сессии берётся уже
после создания и также имеет разные ключи.

**Воспроизведение:**

1. В браузере без сессии открыть приглашение в двух вкладках. Для наглядности —
   крестики-нолики, хозяин уже занимает одно из двух мест.
2. Отправить «Присоединиться» в обеих вкладках до получения ответа первой
   (например, при задержке сети). Оба POST уходят без куки, с разными attempt.
3. Первый запрос создаёт гостя A и занимает последнее место. Второй создаёт гостя B,
   устанавливает его куки на строке 108, затем получает `lobby_full` при вступлении.
4. Если ответ B приходит последним, общей куки браузера становится B. После
   `refresh()`/обновления страницы обе вкладки используют B, который не владеет
   местом A. Место A остаётся занятым. Сервер не завершал сессию A; его уже открытый
   сокет также может продолжать действовать до переподключения или истечения.

**Эффект:** обычный сценарий двух вкладок способен потерять доступ к только что
занятому месту без явного выхода. В лобби с несколькими свободными местами один
человек занимает два места. Это нарушает S05 (один участник и одно место), P05
(одна текущая личность браузера) и требование не подменять её без явного выхода.
Проверка двух вкладок после уже завершённого первого входа эту гонку не покрывает.

**Направление исправления:** координировать первоначальное создание личности между
вкладками: общий устойчивый attempt для незавершённого входа с атомарной координацией
либо общий замок авторизации с повторным чтением текущей сессии перед отправкой.
При этом нельзя повторно использовать завершённый/отозванный attempt как новый
вход. Проверить два конкурирующих запроса до первого Set-Cookie и разные порядки
ответов; после обоих ответов должны остаться одна личность и одно место.

Сценарий подтверждён чтением цепочки `InvitationPage → api.guestJoin → routes →
createGuest → withSession → LobbyService.join` и отдельной повторной проверкой
куки/ключей замков. Динамически не запускался: по поручению тестовую БД не трогал.
Дополнительный субагент для проверки кандидата не запускался по ограничению
поручения; независимой второй проверки именно этого кандидата нет.

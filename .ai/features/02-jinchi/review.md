### R1 — IMPORTANT: палитра и настройки исключены из полноэкранного редактора

`games/jinchi/src/client/MapEditor.tsx:145`,
`games/jinchi/src/client/MapViewport.tsx:184` в исходном срезе.

Fullscreen запрашивается на корне `MapViewport`, а палитра материала, размеры
и симметрия находятся снаружи этого элемента. В native fullscreen они исчезают;
в fallback их закрывает фиксированный viewport. Войти в полный экран, нарисовать
стены, затем выбрать и нарисовать базу без выхода невозможно. Это нарушает основной
сценарий P12/P13: полноэкранное создание большой карты со стенами и стартовыми зонами.

Направление исправления: включить необходимые элементы редактора в toolbar,
который находится внутри fullscreen-корня.

**Статус:** исправлено в рабочем дереве основным исполнителем. Собственный
Chromium-эксперимент с настоящим Fullscreen API подтвердил, что
`document.fullscreenElement` содержит `.jn-palette`, `.jn-editor-settings`
и `.jn-editor-tools`.

### R2 — IMPORTANT: pinch в инструменте «Заливка» меняет карту

`games/jinchi/src/client/MapEditor.tsx:69` в исходном срезе;
связанный путь отмены — `MapViewport.tsx:235` и `MapEditor.tsx:97`.

Заливка фиксировалась прямо на первом pointerdown, до определения жеста двумя
пальцами. При втором пальце viewport вызывал `onStrokeCancel`, но редактор не
сохранял gesture для заливки, поэтому отменять было нечего. На открытой карте
выбор «Заливка»/«Стена» и обычный pinch могли залить всё свободное пространство.
Основной исполнитель подтвердил исходный RED в настоящем мобильном браузере:
площадь 256 → 8, стены 0 → 248. Масштабирование не должно редактировать карту
(P12/P13, фокус ревью плана).

Направление исправления: откладывать commit заливки до завершения одиночного жеста;
pinch/cancel должен завершаться без изменения карты и истории.

**Статус:** исправлено в рабочем дереве основным исполнителем. Собственный
Chromium-эксперимент на 390×844, `hasTouch`, CDP touchStart с двумя пальцами →
touchMove → touchEnd подтвердил: сериализованная карта не изменилась, стен 0 → 0.

### R3 — IMPORTANT: обычный MCP-прогон большой карты надолго блокирует сервер

Вход новой игры: `apps/server/src/games/catalog.ts:10`;
дорогой список ходов — `games/jinchi/src/game.ts:391`;
потребитель — `apps/server/src/mcp/server.ts:88` и `packages/sdk/src/simulate.ts:43`.

Jinchi добавляет поддерживаемую карту 200×200, но общий синхронный `simulate`
по-прежнему выполняет до 2000 действий в каждом из 100 раундов по умолчанию
(до 200 по запросу), без общего вычислительного бюджета. Каждый ход включает
линейный поиск по карте и заливку. Пока цикл выполняется, тот же Node event loop
не обслуживает HTTP, WebSocket и таймеры всех остальных лобби.

Воспроизведение без БД: валидная открытая карта 200×200, одиночные базы `1` в
левом верхнем и `2` в правом нижнем углу; d2, `capture.walls=false`,
`end.skipRounds=0`; `simulate(jinchi, config, {rounds:1})`.
Фактический собственный замер: **3022,5 мс** за один незавершённый раунд
из 2000 действий. Умножение такого пути на стандартные 100 раундов означает
минуты блокировки процесса; полный запрос намеренно не запускался.

Направление исправления: бюджет общей работы, зависящий от площади/стоимости
игры, либо исполнение с уступкой event loop. При остановке по бюджету отчёт должен
различать завершённые, попытанные и не запущенные раунды и сообщать
`budget-exceeded`, не выдавая отсутствие вычисления за `never-ends`.
Ускорение не должно изменять реальные правила конца партии.

**Статус:** исправление готовит основной исполнитель, повторная проверка ожидается.

### R4 — IMPORTANT: «Конец» превью выдаёт промежуточное положение без обозначения

`games/jinchi/src/client/index.ts:24`; связанные потребители —
`apps/web/src/components/ConfigPreview.tsx:32`,
`apps/server/src/mcp/server.ts:114`.

Клиент обрывает игру после 1800 действий и возвращает `MatchView` как результат
`moment='end'`. Контракт `GameClient.previewMatch` обещает завершённый случайный
раунд. В UI нет предупреждения о частичном прогоне, а MCP в этом случае возвращает
`moment: "end", round: "раунд не начат"`, хотя сыграны 1800 ходов.

Тот же валидный конфиг из R3, `previewMatch(config, 'end', 1)`:
**4876,2 мс**, `phase="playing"`, `turn=1800`, счёт `[2713,2729]`,
`lastRound=null`. Кроме неверной маркировки, нажатие превью удерживает главный поток
браузера почти пять секунд; MCP удерживает общий процесс сервера.

Направление исправления: ограничить работу по площади и честно отразить частичное
превью в контракте/руководстве, UI и тексте MCP. Итог/победителя показывать только
для действительно завершённого раунда.

**Статус:** исправление готовит основной исполнитель, повторная проверка ожидается.

# Движок Jinchi

Реализован пакет `@asobiba/game-jinchi`: схема правил v1, схема визуала, чистый движок,
шесть пресетов, руководство MCP и экспорт T02. Клиент, каталоги и корневые зависимости
в этот коммит не входят.

## Правила и контракт

- Карта 3–200 × 3–200, строки `.#1…8`, 2–8 позиций. Валидация строк и размеров не
  падает на незавершённой карте редактора. Предупреждения: закрытые, касающиеся и
  неравные базы, кубики крупнее стороны карты.
- Постановки: оба поворота, выбранное соседство, перекрытие своих клеток только с
  новой свободной клеткой. Проверка сервера и клиентский `placementError` одинаковы.
- Захват: итеративные компоненты; диагональное кольцо задаёт 4/8 соседей; стены
  проходимы только при обнаружении окружения в режиме «только свои клетки».
  Все равные максимальные соседние компоненты остаются открытыми. Чужие клетки
  забираются с выбранной защитой, нулевой счёт исключает игрока из дальнейших ходов.
- Автобросок и ручной бросок, автоматические пропуски, полные круги оставшихся
  игроков, последовательные круги без постановок, лимит кругов, доля карты,
  разделённая карта и последний игрок. Лучшие равные счета — ничья лидеров.
- `passTurn` обслуживает таймер SDK. Ручной бросок не меняет `turnId`, поэтому
  случайная политика SDK успевает бросить и поставить в рамках одного хода.
- T02 сохранён. Дополнительные необязательные сериализуемые поля состояния:
  `cycleSeats`, `cyclePlaced`, `skippedCycles`. Они нужны для точных кругов после
  выбывания; необязательность позволяет собирать статические UI-fixture без них.
  Список legal в view отсутствует. Лента ограничена 100 событиями с монотонными id.

## Защита длинных серий неудачных бросков

После 256 последовательных неудачных автобросков движок вычисляет все возможные
упорядоченные пары кубиков для каждого оставшегося игрока. Если вероятность полного
неудачного обхода равна q, число таких обходов выбирается геометрически; затем
выбираются первый успешный игрок с весом произведения предшествующих неудач и его
равномерная допустимая пара. Пропущенные броски берутся равномерно из неудачных пар,
считаются в кругах и лимитах и проходят через ту же ленту из последних 100 событий.
Так сохраняется распределение независимых честных кубиков, а обработка не зависит
от потенциально бесконечной серии отбраковки. Случайность только из `ctx.rng`.
Решение отражено в руководстве игры; прямого принудительного броска 1:1 нет.

## Проверки

- TDD: первый красный запуск зафиксировал отсутствующий модуль, затем отдельные
  красные утверждения — границы карты редактора и лимит кругов при ускорении RNG.
  Один ранний провал был ошибкой fixture: повёрнутая фигура действительно заходила
  на стену; fixture исправлена, ожидаемое правило не менялось.
- `npx vitest run --config storage/verification/02-jinchi/unit.vitest.config.ts games/jinchi/src/game.test.ts`:
  **33/33**. Лог всех красных и зелёных запусков:
  `storage/verification/02-jinchi/engine-tests.log`.
- `npx tsc --noEmit`: код 0 после исправления вывода типа строк в пресетах.
- Все 6 пресетов: по 10 дополнительных случайных партий, **60/60** завершились,
  `stuck`, `never-ends`, `illegal-legal-action` отсутствуют. Максимум действий:
  Дуэль 26, Четыре угла 59, Крепости 73, Лабиринт 328, Материк 563,
  Восьмигранники 286.
- Поиск обоих поворотов 6×4 на 200×200: **0,8–6,7 мс** за 10 запусков, 8 якорей.
  Дополнительно тестируется захват компоненты в 10000 клеток на 200×200 без рекурсии.
  Замеры: `storage/verification/02-jinchi/engine-performance.log`.
- Оптимизированный поиск сравнивается с независимой проверкой каждой постановки
  на смешанных картах для обоих режимов соседства и перекрытия.
- `Match.restore` воспроизводит случайные базы, броски, ходы и таймер random.

Полный QG и живые сайт/WebSocket/MCP/PNG выполняются интегратором после сборки
клиента. Общий suite здесь не запускался по инструкции координатора: его globalSetup
пересоздаёт общую проверочную БД.

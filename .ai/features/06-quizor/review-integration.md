## Подтверждённые находки

### R-I01 — IMPORTANT: медийные элементы справа в соответствии не отображаются

- Место: `games/quizor/src/client/AnswerForm.tsx:352` (вывод `f.right` в `option`).
- Вход: допустимое поле `match`, слева текст, справа элементы
  `{id:"r1",asset:"ast_flag0001",media:"image"}` и
  `{id:"r2",asset:"ast_anthem01",media:"audio"}`, без текста.
- Ожидание: поддержанные схемой картинки/звуки позволяют человеку выбрать соответствие;
  план задачи 4 требует возможности сыграть все поддержанные форматы. `itemSchema`
  одинаково разрешает asset/media для left и right (`rules.ts:287,360–361`).
- Фактически: справа выводится только `x.text ?? x.id`. После Zod `text` равен пустой
  строке; `<option>` пуст. Ни изображения, ни плеера/URL правых элементов в DOM нет.
  Пользователь видит два неразличимых пустых варианта и может только угадывать.
- Доказательство: отдельный readonly probe через `node --import tsx` пропустил конфиг
  через настоящий rulesSchema и renderToStaticMarkup(AnswerForm). Результат:
  `imageIncluded:false`, `audioIncluded:false`,
  `<option value="r1"></option><option value="r2"></option>`.
  Текущий AnswerForm.test проверяет только текстовый right и этого не замечает.
- Исправление: показать правое множество отдельными карточками с Option (картинка,
  аудиоплеер, понятный номер/подпись), а select связать с этими карточками либо заменить
  контролом, который действительно показывает медиа. Не полагаться на media внутри
  native option.

- Доказательство: readonly probe с настоящими rulesSchema, quizor.setup/view,

### R-I03 — IMPORTANT: пауза теряет последний черновик на сервере, хотя поле восстановлено

- Место: `games/quizor/src/client/Board.tsx:76–89` — cleanup отменяет отложенный draft;
  восстановление начального value на строках 66–70 не отправляет его заново.
- Сценарий: включены таймер и autoSubmit; игрок допечатывает верный ответ, менее чем
  через 200 мс хозяин ставит паузу. После resume игрок видит свой ответ, ничего не меняет
  и ждёт окончания таймера.
- Ожидание: P40 сохраняет черновик, P11 отправляет введённый неотправленный ответ при
  истечении времени.
- Фактически: change немедленно сохраняет ответ только в local draftCache, а серверный
  draft отложен на 200 мс. Пауза удаляет QuestionAnswer из дерева (`Board.tsx:591`),
  cleanup отменяет отправку. После продолжения форма восстанавливает локальный cached
  value (`Board.tsx:865–873`), но change/onDraft/draft не вызываются. Сервер имеет прежний
  draft или пустой ответ; closeQuestion использует только s.drafts (`game.ts:1265`).
  Видимый верный текст получает оценку за старый ответ или молчание. То же окно возникает
  при временной потере связи во время последней отправки draft.
- Проверка: причинная цепочка повторно прочитана от onChange, debounce и unmount до
  восстановления value и серверного autoSubmit; прямого браузерного прогона этого
  узкого 200-мс окна ревьюер не запускал. Root получил сценарий для адресной регрессии.
- Исправление: обеспечить доставку последнего локального draft при продолжении/восстановлении
  связи и не отменять его без последующей синхронизации. Учесть, что отправка только из
  unmount на уже установленной паузе может быть отклонена сервером.

### R-I04 — IMPORTANT: автоматический показ медиа обрывается через условные 10 секунд

- Место: `games/quizor/src/rules.ts:633–646`, особенно `block.to ?? from + 10`.
- Вход: audio/video без to и durationSeconds (оба необязательны по схеме), например
  минутный WAV или длинное видео из поддержанного собственного пула, pacing:auto.
- Ожидание: P18 — автоматическая смена медиа по окончании; P20 явно включает большие
  ролики и WAV. Если границы не заданы, проигрывается весь файл.
- Фактически: blockDuration возвращает 10 секунд независимо от настоящей длины.
  Движок переключает блок и открывает вопрос через 10 секунд, клиент Media получает
  active:false и ставит файл на паузу (`Blocks.tsx:97`). Короткий файл, напротив, оставляет
  необоснованное ожидание до 10 секунд. repeat/speed умножают эту вымышленную длительность.
  Asset metadata содержит только MIME/размеры/байты, поэтому реальная длительность
  на следующем серверном этапе не восстанавливается.
- Проверка: повторное чтение schema → blockDuration → управление active Media; root
  отдельно подтвердил несоответствие P18. Длинный реальный файл в рамках этого ревью
  не загружался, общий live playback проверял 2-секундный WAV и 5-секундный MP4.
- Исправление: определить длительность при проверке/замораживании конфига по достоверным
  метаданным файла либо потребовать явную длину с понятной ошибкой. Нормализованное время
  должно использоваться движком, клиентом, повторами и preview одинаково.

### R-I05 — IMPORTANT: после перезапуска сервера завершённый квиз теряет доступный разбор

- Место: `apps/server/src/lobbies/service.ts:94–100` — ленивое создание room всегда
  устанавливает match:null; `restoreAll` на строке 571 выбирает только playing-лобби.
- Сценарий: закончить Quizor, перезапустить сервер, открыть ту же ссылку лобби.
- Ожидание: P34 — разбор каждого вопроса с правильным ответом и ответами всех можно
  пролистать после игры. Журнал завершённой партии уже хранится в БД.
- Фактически: room сохраняет только id/места последней партии, не восстанавливает Match;
  sendMatch (`service.ts:524`) отправляет match:null. Завершённые лобби не проходят
  restoreAll, так что кнопка возврата на доску и history отсутствуют. Восстановление
  завершённого Match внутри canReadAsset (`service.ts:194–200`) применяется только
  к файловому ACL и не заполняет комнату/данные для клиента.
- Проверка: root сообщил наблюдение после реального restart; ревьюер независимо
  подтвердил цепочку room → restoreAll → sendMatch по исходникам проверяемого HEAD.
- Исправление: по открытию законченного лобби восстановить последнюю завершённую
  пошаговую партию из журнала и отправить viewer-safe finished MatchView. Не менять
  lobby.status и не запускать новую партию. Проверить чтение после рестарта отдельным
  игроком/зрителем с сохранением showAnswers и остальных ограничений вида.

### R-I06 — IMPORTANT: запоздалый начальный HTTP-снимок возвращает активную партию в waiting

Это существовавшая до `7cb5fc2` общая гонка сайта, а не новая регрессия исправлений.
Она включена по отдельному запросу координатора после реального наблюдения на Quizor.

- Место в `7cb5fc2`: `apps/web/src/pages/LobbyPage.tsx:147` — безусловный
  `setLobby(res.lobby)` начального GET; socket.lobby переносится в state отдельным
  effect на строках 162–164.
- Сценарий: начальный GET захватил waiting и задержался; за это время WebSocket
  прислал playing + match, другой участник начал партию; затем старый GET завершился.
- Последствие: GET перезаписывает playing на waiting. match продолжает обновляться,
  но ссылка socket.lobby при match-only сообщениях не меняется, поэтому синхронизирующий
  effect не срабатывает вновь. Условие сцены на строках 449–455 ложно; доска остаётся
  в обычном лобби без stage/fullscreen-сцены до следующего lobby push или reload.
  Нарушается обязательная сцена начавшейся партии. Это не краткий промежуточный render.
- Детерминированный readonly probe без DOM/hook harness воспроизвёл именно порядок
  разрешения Promise и те же присваивания/предикат сцены: WebSocket playing → поздний
  GET waiting → match-only push. Результат исходного кода:
  `afterHttp={status:"waiting",stage:false}`,
  `afterMatchOnly={status:"waiting",stage:false}`.
- Проверен добавленный root guard в рабочем дереве: начальный GET заполняет state только
  при отсутствии текущего лобби с тем же id; socket effect принимает только свой id.
  Та же последовательность дала
  `afterHttp={status:"playing",stage:true}`,
  `afterMatchOnly={status:"playing",stage:true}`. Для перехода между лобби отдельная
  проверка id не позволяет старому socket snapshot занять новый экран.
- Адресная регрессия: задержать первый GET с waiting, доставить socket playing+match,
  разрешить старый GET, затем прислать только match; сцена должна оставаться открытой
  и lobby.status — playing. Исправление не требует дублирования DOM/React в тестовом
  harness; достаточно существующей поверхности/выделенной функции выбора снимка.
